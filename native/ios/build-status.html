Les 4 onglets

construits à fond, par votre propre décision de séquençage
Construit

Accueil

  • Bandeau palier (Habitué/Privilégié/Ambassadeur) avec barre de progression vers le palier suivant
  • Solde de points, visites, dépenses totales
  • Prochaine récompense accessible (jauge radiale)
  • Fil des offres actives du restaurant
  • Historique récent des transactions de points
  • Pull-to-refresh, état de chargement, erreur réseau distincte
Construit

Commander

  • Menu groupé par catégorie, images/description/prix
  • Compteurs de quantité par article avec retour haptique
  • Barre de panier persistante (total, nombre d'articles)
  • Checkout complet : pourboire (0/10/15/20 %), taxes, note de paiement
  • Commande envoyée dans la vraie file /commandes du restaurant
  • États succès / échec / hors-ligne distincts
Construit

Récompenses

  • Catalogue avec affordabilité en temps réel, confirmation avant échange
  • Codes de récompenses en attente à montrer en salle
  • Section parrainage : cartes de programme, barre de progression, génération de QR native, partage système
Construit

Profil

  • Carte identité avec palier, points, visites
  • Préférences de notification (Tout / L'essentiel)
  • Liens légaux fonctionnels (CGU, confidentialité) — visionneuse in-app
  • Déconnexion
  • Suppression de compte (irréversible, confirmation par saisie)

Authentification & premier lancement

Construit

Écran de connexion

  • Réplique exacte du /portal/login web (même carte, même fond crème, même copy)
  • Code à 6 chiffres par courriel (Resend, pas Supabase par défaut), auto-vérification
  • Validation d'adresse en direct, cooldown de renvoi 30 s
  • Consentements réels (CGU obligatoire, marketing optionnel) avec liens cliquables
Construit

Splash & onboarding

  • Écran de lancement natif (logo + fond de marque, pas l'écran par défaut Xcode)
  • Intro plein écran pour un nouveau visiteur
  • Carrousel d'accueil (paliers, progression) affiché une seule fois
  • Transitions animées entre tous les écrans (plus de coupures abruptes)
Partiel

Fournisseurs de connexion

  • Courriel + code : fonctionnel de bout en bout
  • Google / Facebook : non branchés — nécessite votre action (voir plus bas)
  • OTP par SMS : reporté par votre choix, nécessite un fournisseur payant type Twilio

Architecture backend

Fait
Pont Bearer token ↔ RLS

4 routes (/api/portal/menu, orders, account, referrals) exposent au natif exactement ce que la session cookie expose au web, avec le même client scopé au token — jamais le client admin pour une lecture qui doit rester filtrée par ligne.

Fait
Emails transactionnels via Resend

Le hook « Send Email » Supabase route tous les courriels (OTP client, autres actions) vers des gabarits de marque, plus par le générique Supabase.

Fait
RLS corrigée

customers_update_own ajoutée — le profil client pouvait techniquement s'enregistrer sans jamais rien sauvegarder avant cette correction.

Partiel
Seuils de palier personnalisés par restaurant

Le natif utilise les seuils par défaut (150 $ / 400 $) partout — un restaurant qui personnalise ses paliers verrait un décalage entre web et natif tant qu'un pont pour ce réglage n'existe pas.

Défensif & robustesse

En place

Réseau

  • Timeout 15 s sur chaque appel pont, jamais un spinner infini
  • Distinction « hors-ligne » vs « erreur serveur » avec message actionnable dans chaque cas
  • Un échec de rafraîchissement garde les dernières données valides à l'écran plutôt que de vider la page
En place

Sécurité

  • RLS = la vraie frontière de confiance, identique web et natif (jamais une vérification uniquement côté client)
  • Le bypass de connexion développeur est compilé hors des builds Release (#if DEBUG) — ne peut pas atterrir sur TestFlight ni l'App Store
  • Suppression de compte : purge des données identifiantes, conserve l'historique transactionnel du restaurant
Manquant

Pas encore couvert

  • Pas de tests automatisés (unitaires ou UI) sur le projet natif
  • Pas de rapport de crash (Sentry / Crashlytics ou équivalent) branché
  • Pas de vérification d'accessibilité (VoiceOver, contrastes, Dynamic Type) menée systématiquement

Ce qui exige une action de votre part

rien de tout ceci n'est automatisable sans vos identifiants/décisions
01

Compte Apple Developer Program (99 $ US/an)

Le sideload actuel fonctionne avec votre Apple ID personnel gratuit. La distribution App Store ou TestFlight externe exige l'inscription payante au Developer Program, faite depuis votre propre compte sur developer.apple.com.

02

Identifiants Google & Facebook Login

Créer les apps OAuth (Google Cloud Console + Meta for Developers), obtenir client ID/secret, et me les fournir comme variables d'environnement — je branche le code ensuite. Une documentation pas-à-pas peut être préparée séparément si vous voulez configurer « en one shot » comme demandé précédemment.

03

Fournisseur SMS (Twilio ou équivalent) pour OTP par texto

Reporté par votre propre choix précédent (« email seulement pour l'instant »). Nécessite un compte payant et un numéro vérifié avant que je puisse le brancher à Supabase Auth.

04

Contenu de fiche App Store Connect

Captures d'écran finales, description marketing, URL de politique de confidentialité publique, catégorie d'âge, coordonnées de support — ce sont des choix de contenu/marque qui vous reviennent, pas du code.

05

Décision : élargir maintenant ou rester sur les 4 onglets

Le hook de session redemande widgets/biométrie/push/QR/localisateur comme s'ils étaient dus maintenant, mais votre propre choix explicite était de finir les 4 onglets d'abord. Dites-moi si cette décision tient toujours ou si l'un de ces éléments passe en priorité.
